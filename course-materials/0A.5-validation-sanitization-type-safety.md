# Level 0A.5 — Validation, Sanitization & Type Safety

## 1. Schema Validation of Request Inputs (Zod Middleware)

In production REST APIs, unvalidated incoming HTTP request data (`req.body`, `req.params`, `req.query`) is untrusted external input. Processing unvalidated inputs leads to server crashes, invalid database states, prototype pollution, and security vulnerabilities.

### The Request Validation Middleware Pattern
Validation should happen at the **route boundary** before execution enters controller functions or service layers.

```
 [ HTTP Request ] (body / params / query)
        │
        ▼
 ┌────────────────────────────────────────────────────────┐
 │ validateRequest(schemas) Middleware                    │
 │  - Validates req.body, req.params, req.query           │
 │  - Strips unknown properties (.passthrough vs .strip) │
 │  - Replaces req values with parsed & typed data       │
 └───────────────────────────┬────────────────────────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
      [ Valid Input ]                  [ Invalid Input ]
            │                                 │
            ▼                                 ▼
┌───────────────────────┐         ┌───────────────────────┐
│ Next(Controller)      │         │ BadRequestError (400) │
│ Typed Request Payload │         │ RFC 7807 Detail Field │
└───────────────────────┘         └───────────────────────┘
```

## 2. Strict Type Safety: DTOs & Zero `any`

### Data Transfer Objects (DTOs)
DTOs define the strict contract for data entering or leaving API boundaries:
- **Input DTOs**: Inferred directly from Zod validation schemas (`z.infer<typeof createSchema>`).
- **Output DTOs / Serializers**: Prevent accidental leakage of sensitive internal fields (e.g. `password_hash`, `internal_id`, `deleted_at`).

### Strict Typing Rules:
1. **Never use `any`**: Using `any` disables TypeScript's type checker and propagates untyped variables across service boundaries. Use `unknown` for raw unvalidated inputs, then narrow with Zod.
2. **Strict Property Invalidation**: Zod schemas by default strip unrecognized fields from incoming JSON payloads (`.strip()`), mitigating mass-assignment vulnerabilities (where malicious clients inject unauthorized fields like `isAdmin: true`).

## 3. Injection Attack Vectors & Prevention Strategies

| Attack Vector | Mechanism | Prevention / Mitigation |
| :--- | :--- | :--- |
| **SQL Injection (SQLi)** | Malicious SQL syntax injected via raw string concatenation (`SELECT * FROM users WHERE email = '` + email + `'`) | Parameterized queries (`$1, $2`), ORMs/Query Builders (Kysely/Prisma/Knex) |
| **NoSQL Injection** | Injecting operator objects into MongoDB queries (e.g. `{ "username": { "$ne": null } }`) | Zod type coercion enforcing scalar strings for inputs, sanitizing object prototypes |
| **Cross-Site Scripting (XSS)** | Injecting executable HTML/JavaScript tags into stored database fields | Input sanitization, contextual output encoding, and setting HTTP `Content-Security-Policy` headers |
| **HTTP Parameter Pollution (HPP)** | Supplying duplicate query parameters (`?id=1&id=2`) resulting in arrays instead of strings | Zod strict schema checking (`z.string()`) rejecting unexpected arrays |
