# Level 0A.6 — Structured Concurrency & Advanced Async Patterns

## 1. Advanced Promise Execution Controls

In Node.js backend engineering, managing multiple asynchronous operations concurrently requires selecting the correct Promise combinator. Using the wrong combinator leads to silent failure swallows, uncaught rejections, or cascading resource leaks.

```
                  ┌─────────────────────────────────────────┐
                  │        Incoming Async Workloads         │
                  └────────────────────┬────────────────────┘
                                       │
     ┌──────────────────┬──────────────┴───────┬──────────────────┐
     ▼                  ▼                      ▼                  ▼
┌──────────┐    ┌─────────────────┐    ┌───────────────┐    ┌──────────┐
│  all()   │    │  allSettled()   │    │     any()     │    │  race()  │
└────┬─────┘    └────────┬────────┘    └───────┬───────┘    └────┬─────┘
     │                   │                     │                 │
Fail-Fast        Resilient Batch       First Success        First Result
All Must Succeed Returns All Outcomes  Fails only if ALL    Succeeds or fails
Or 1st Fails     (Fulfilled/Rejected)  promises reject      on 1st settlement
```

### Comparative Summary Table

| Combinator | Behavior on Resolution | Behavior on Rejection | Production Use Case |
| :--- | :--- | :--- | :--- |
| `Promise.all([p1, p2])` | Waits for **ALL** to fulfill; returns array of results `[r1, r2]`. | **Fails Fast**: Immediately rejects on the **FIRST** rejection; ignores pending promises. | Atomic batch ops where every step is mandatory (e.g. fetching user profile + user settings together). |
| `Promise.allSettled([p1, p2])` | Waits for **ALL** to settle regardless of outcome. | **Never Rejects**: Returns array of outcome objects `{ status: 'fulfilled', value }` or `{ status: 'rejected', reason }`. | Bulk notification dispatch, multi-provider metric collection, partial-failure bulk exports. |
| `Promise.any([p1, p2])` | Resolves on the **FIRST** fulfilled promise. | Rejects **ONLY IF ALL** promises reject; throws `AggregateError`. | Fallback redundancy queries (e.g. querying primary DNS / secondary DNS, calling primary vs fallback payment gateway). |
| `Promise.race([p1, p2])` | Settles on the **FIRST** promise that settles (fulfilled OR rejected). | Rejects immediately if the first promise to settle is a rejection. | Enforcing request timeouts on async operations (`Promise.race([fetchPromise, timeoutPromise])`). |

## 2. Request & Query Cancellation with `AbortController` / `AbortSignal`

When an HTTP client cancels a request (e.g. closes browser tab, navigation timeout), continuing long-running database queries, downstream microservice calls, or AI generation tasks wastes server CPU, memory, and database connection pool slots.

### Propagation Flow with `AbortController`

```
 [ Client Disconnects / Aborts ]
               │ (HTTP Socket Close Event)
               ▼
   [ Express req.on('close') ]
               │
               ▼
 [ AbortController.abort() ] ──(Signals AbortSignal)──┐
                                                     │
       ┌─────────────────────────────────────────────┴─────────────────────────────┐
       ▼                                             ▼                             ▼
 [ fetch(url, { signal }) ]             [ Stream Processing Pipeline ]      [ Database Driver ]
 (Cancels HTTP socket)                  (Destroys Stream Reader)           (Sends Cancel Signal)
```

### TypeScript Pattern: Propagating `AbortSignal`

```typescript
import { Request, Response, NextFunction } from 'express';

export async function fetchWithCancellation(
  url: string,
  parentSignal?: AbortSignal
): Promise<unknown> {
  const controller = new AbortController();

  // Link parent signal (e.g. HTTP request abort) to child controller
  if (parentSignal) {
    if (parentSignal.aborted) {
      controller.abort(parentSignal.reason);
    } else {
      parentSignal.addEventListener('abort', () => controller.abort(parentSignal.reason), {
        once: true,
      });
    }
  }

  const response = await fetch(url, { signal: controller.signal });
  return response.json();
}
```

## 3. Advanced `AsyncLocalStorage` Contexts & Multi-Tenancy

Beyond correlation IDs, `AsyncLocalStorage` enables request-scoped contextual state across asynchronous boundaries without parameter drilling:

1. **Request-Scoped Database Transactions**: Storing active transaction handles (`pg.Client` / `EntityManager`) so repository methods automatically execute within the current HTTP request's active transaction block.
2. **Multi-Tenant Scope Propagation**: Propagating `tenantId` into database query filters automatically to prevent cross-tenant data leaks.
3. **Feature Flag Context**: Threading user cohort & feature flag overrides through execution pipelines without passing `userContext` into every service function signature.

## 4. Structured Concurrency Discipline

### The Background Task Orphan Anti-Pattern
Launching floating promises without tracking or awaiting them:

```typescript
// ❌ DANGEROUS ANTI-PATTERN: Unhandled orphan promise
app.post('/orders', (req, res) => {
  createOrder(req.body); // Returns Promise<Order>
  sendConfirmationEmail(req.body.email); // ⚠️ Floating promise! If this rejects, it triggers unhandledRejection
  res.status(201).json({ status: 'created' });
});
```

### Structured Concurrency Rules:
1. **Parent Joins Child**: Parent functions must not complete until all child asynchronous operations have either completed, settled, or been explicitly delegated to a managed background job queue (e.g. BullMQ / Kafka).
2. **Explicit Lifecycles**: Fire-and-forget tasks in HTTP handlers must be wrapped in error-handling wrappers or pushed to background worker pools with explicit logging and metric counters.

## 5. Async Concurrency Bounding (`p-limit` & Backpressure)

Running `Promise.all(10000.map(fetch))` overwhelms socket pools, triggers `EMFILE` (too many open files) or database connection pool exhaustion.

### Rate Limiting Concurrency with Bounded Pools

```typescript
import pLimit from 'p-limit';

// Limit concurrent database/network operations to maximum 5 at a time
const limit = pLimit(5);

const tasks = itemIds.map((id) =>
  limit(async () => {
    return await fetchItemDetails(id);
  })
);

// Runs all tasks with max concurrency of 5
const results = await Promise.all(tasks);
```

### Parallelism vs Concurrency in Node.js
- **Concurrency (Single-Threaded Event Loop)**: Interleaving asynchronous I/O tasks on a single OS thread via non-blocking Libuv event loop.
- **Parallelism (Worker Threads / Multi-Process)**: Executing CPU-heavy computation (image processing, crypto, large JSON parsing) simultaneously across multiple physical CPU cores via `worker_threads` or process clusters.
