# Level 0A.0 — Node.js Concurrency & Event Loop Mental Model

## 1. Single-Threaded Concurrency Model

### Why Node.js? (Node vs Java vs Go)
Traditional web servers (like Tomcat in Java) historically used a **Thread-per-Request** model:
- Every incoming HTTP request allocates a OS thread.
- If 1,000 requests are waiting on slow database queries, 1,000 OS threads are spawned or pulled from a pool.
- **Cost**: Each OS thread consumes ~1MB of stack memory. 1,000 threads = ~1GB RAM just for idle thread stacks! Furthermore, OS context-switching between 1,000 threads burns significant CPU cycles.

**Go (Goroutines)**:
- Uses an **M:N Scheduler** (M green threads mapped onto N OS threads).
- Goroutine stacks start tiny (~2KB) and grow dynamically. Context switching happens in user space.

**Node.js (Event-Driven Non-Blocking I/O)**:
- Node.js runs JavaScript on a **single main thread** (the V8 execution thread).
- Instead of waiting synchronously for I/O (database, disk, network), Node delegates I/O calls to the OS kernel (via `epoll`/`kqueue`/`IOCP`) or to libuv's background worker pool.
- When I/O completes, an event callback is pushed to the Event Loop queues.
- **Result**: Node can handle tens of thousands of concurrent connections on a single OS thread with minimal memory overhead.

```
       +---------------------------------------------------------+
       |               Main V8 Thread (Single Thread)            |
       |  [ Execution Stack ] ---> Executes JS Code Synchronously |
       +---------------------------------------------------------+
                                    |
            +-----------------------+-----------------------+
            | Async I/O Operations  | Crypto / FS Work      |
            v                       v                       v
    +---------------+       +------------------+   +-------------------+
    | Kernel epoll/ |       | Libuv Thread     |   | Micro/Macrotask   |
    | kqueue / IOCP |       | Pool (4 threads) |   | Event Queues      |
    +---------------+       +------------------+   +-------------------+
```

## 2. Event Loop Phases, Microtasks & Macrotasks

The Node.js event loop has distinct phases and queue priorities:

```
   ┌───────────────────────────┐
┌─>│           timers          │ <-- setTimeout, setInterval
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     pending callbacks     │ <-- I/O callbacks deferred to next loop
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │        idle, prepare      │ <-- Internal libuv house-keeping
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           poll            │ <-- Retrieve new I/O events; execute I/O callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           check           │ <-- setImmediate callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │      close callbacks      │ <-- socket.on('close', ...)
└──┴─────────────┬─────────────┘
```

### The Priority Hierarchy (Microtasks vs Macrotasks)

Before moving between ANY phase of the Event Loop (and after every single synchronous C++ / JS stack frame clears), V8 drains the **Microtask Queues**:

1. **`process.nextTick()` Queue** (Highest Priority):
   - Not technically part of libuv; managed by Node.js.
   - Executes immediately after the current operation finishes, before any other microtasks or macrotasks.
   - **Danger**: Recursive `process.nextTick()` calls starve the Event Loop completely, freezing all I/O!

2. **Promise Microtask Queue** (Standard Microtasks):
   - `.then()`, `.catch()`, `.finally()`, and resumed `await` continuations.
   - Drained completely before the Event Loop moves to the next phase or picks up the next macrotask.

3. **Macrotasks** (Event Loop Phases):
   - Timers (`setTimeout`) $\rightarrow$ Poll (I/O) $\rightarrow$ Check (`setImmediate`).

## 3. `async/await` Execution Mechanics & Express Error-Handling Bug

### How `async/await` works under the hood
`async/await` is syntactic sugar built over Promises and Generators:
- Marking a function `async` wraps its return value in `Promise.resolve()`.
- When execution hits `await expr`:
  1. `expr` is evaluated.
  2. The remainder of the `async` function is suspended and registered as a microtask callback when the promise settles.
  3. Control immediately yields back to the caller (or main thread).

### Code Trace & Predictable Execution Order

```typescript
console.log('1: Sync start');

setTimeout(() => {
  console.log('2: Macrotask (setTimeout)');
}, 0);

setImmediate(() => {
  console.log('3: Macrotask (setImmediate)');
});

Promise.resolve().then(() => {
  console.log('4: Microtask (Promise.then)');
});

process.nextTick(() => {
  console.log('5: Microtask (process.nextTick)');
});

(async () => {
  console.log('6: Async func sync start');
  await Promise.resolve();
  console.log('7: Async func after await (Microtask)');
})();

console.log('8: Sync end');
```

**Exact Output Order**:
1. `1: Sync start`
2. `6: Async func sync start` (Synchronous code inside async function runs immediately until `await`)
3. `8: Sync end` (Synchronous script execution finishes)
4. `5: Microtask (process.nextTick)` (`nextTick` queue drained first)
5. `4: Microtask (Promise.then)` (Promise microtask queue drained next)
6. `7: Async func after await (Microtask)` (`await` continuation microtask drained)
7. `2: Macrotask (setTimeout)` or `3: Macrotask (setImmediate)` (Timers / Check phase depending on I/O context)

### Why Async Microtask Bugs Break Express Error Middleware

In Express 4.x, route handlers do **NOT** automatically catch rejected promises from async functions!

```typescript
// ❌ Dangerous Express 4 Pattern
app.get('/users/:id', async (req, res, next) => {
  const user = await database.findUser(req.params.id); // If this throws/rejects...
  res.json(user);
});
```

**Why it fails**:
- The async function returns an unhandled rejected Promise into the microtask queue.
- Express synchronous wrapper never received `next(err)` call because the error occurred asynchronously after the function yielded.
- The HTTP request hangs until client timeout, and an `UnhandledPromiseRejection` is emitted on the Node process.

**The Fix (Express 4 `asyncHandler` pattern)**:
```typescript
const asyncHandler = (fn: Function) => (req: Request, res: Response, next: NextFunction) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

// ✅ Safe Express 4 Pattern
app.get('/users/:id', asyncHandler(async (req, res, next) => {
  const user = await database.findUser(req.params.id);
  res.json(user);
}));
```

## 4. Production Anti-Patterns & CPU Starvation

1. **Synchronous CPU Blocking**:
   - `JSON.parse()` or `JSON.stringify()` on massive payloads (e.g. 50MB JSON).
   - RegEx Catastrophic Backtracking (ReDoS).
   - Synchronous filesystem methods (`fs.readFileSync`) in HTTP handlers.
   - **Impact**: Completely halts the main thread. ALL connected clients freeze; health check endpoints fail, causing Kubernetes to crash loop the container.

2. **Microtask Queue Starvation**:
   - Unbounded recursive Promises or `process.nextTick()` loops preventing libuv from polling network sockets.

## 5. Summary Cheat-Sheet

| Queue / Phase | Mechanism | Execution Priority | Typical Use Case |
|---|---|---|---|
| **Sync Execution Stack** | V8 Call Stack | 0 (Immediate) | Regular JavaScript code execution |
| **`process.nextTick`** | Node Microtask Queue | 1 (Before standard microtasks) | Emergency error cleanup, API consistency guarantees |
| **Promise Microtasks** | V8 Microtask Queue | 2 (Before next Event Loop phase) | `async/await` continuations, `.then()` callbacks |
| **Timers Phase** | Libuv Macrotask | 3 (Event Loop phase) | `setTimeout`, `setInterval` |
| **Poll Phase** | Libuv Macrotask | 4 (Event Loop phase) | Incoming HTTP requests, DB queries, Socket I/O |
| **Check Phase** | Libuv Macrotask | 5 (Event Loop phase) | `setImmediate` (runs right after Poll phase) |
