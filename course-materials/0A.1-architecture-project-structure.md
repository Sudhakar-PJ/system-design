# Level 0A.1 — Clean Layered Architecture & Dependency Injection

## 1. Clean Layered Architecture Overview

In production backend engineering, tight coupling between HTTP routers, business logic, and database access leads to brittle code, untestable modules, and vendor lock-in.

Clean Layered Architecture enforces strict unidirectional dependencies:

```
[ HTTP Request ]
       │
       ▼
┌──────────────┐     Decodes request params/body; validates input schema
│  Controller  │ ◄── Does NOT execute business logic or raw SQL
└──────┬───────┘
       │ Calls Service methods
       ▼
┌──────────────┐     Contains domain rules, orchestration, transaction management
│   Service    │ ◄── Does NOT know about Express (req/res) or database syntax
└──────┬───────┘
       │ Calls Repository interface methods
       ▼
┌──────────────┐     Encapsulates data access (SQL queries, Redis calls, ORM)
│  Repository  │ ◄── Implements a swappable data storage interface
└──────┬───────┘
       │ Executes queries
       ▼
┌──────────────┐
│  DB / Engine │ (Postgres, MongoDB, In-Memory)
└──────────────┘
```

---

## 2. The Golden Rules of Layer Separation

1. **Controllers**:
   - Know **HTTP** (`req`, `res`, HTTP status codes, headers).
   - Should NEVER contain database queries, SQL, or complex business math.
   - Delegates work to Services and returns standardized responses.

2. **Services**:
   - Know **Business Logic** (e.g., "calculating order totals", "checking user eligibility", "orchestrating notifications").
   - NEVER touch HTTP objects (`req`, `res`, status codes). A Service method can be called from an HTTP controller, a CLI command, a gRPC handler, or a background Kafka consumer without modification.

3. **Repositories**:
   - Know **Data Persistence** (Postgres, MongoDB, Redis, external APIs).
   - Expose clean domain methods (`findById`, `save`, `delete`) hiding the underlying data access mechanism.

4. **Dependency Inversion Principle (DIP)**:
   - High-level modules (Services) should not depend on low-level modules (PostgresRepository). Both should depend on **Abstractions (Interfaces)**.

## 3. Manual Constructor Dependency Injection (DI)

Instead of instantiating database instances inside services using `new PostgresRepository()`, we pass dependencies into constructor functions:

```typescript
// 1. Interface definition
export interface IUserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<User>;
}

// 2. Service accepting dependency via constructor
export class UserService {
  constructor(private readonly userRepo: IUserRepository) {}

  async getUserProfile(id: string): Promise<User> {
    const user = await this.userRepo.findById(id);
    if (!user) {
      throw new Error('User not found');
    }
    return user;
  }
}

// 3. Composition Root (instantiating and wiring up layers)
const userRepo = new PostgresUserRepository(dbClient);
const userService = new UserService(userRepo);
const userController = new UserController(userService);
```

## 4. Architecture Decision Records (ADRs)

An **ADR** is a lightweight document describing an architectural choice, its context, and its consequences. ADRs prevent "architecture amnesia" in engineering teams.

### ADR Template Format

```markdown
# ADR-001: Clean Layered Architecture & Manual Constructor DI

## Status
Accepted

## Context
Our application needs to support multiple database backends and mockable unit testing without relying on monkey-patching or complex global state.

## Decision
We adopt a 4-tier clean architecture (`Routes → Controllers → Services → Repositories`) using TypeScript interfaces and manual constructor dependency injection.

## Consequences
- **Positive**: High testability; repositories can be mocked effortlessly in unit tests.
- **Positive**: Clear separation of concerns; HTTP logic isolated from domain rules.
- **Negative**: Slightly more boilerplate (interfaces, factory wiring in composition root).
```
