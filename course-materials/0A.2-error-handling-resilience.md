# Level 0A.2 — Error Handling & Resilience

## 1. Centralized Error Architecture Mental Model

In Node.js/Express backends, unhandled errors lead to crashed processes, unhelpful generic `500 Internal Server Error` responses, or dangerous stack trace leakage to clients. A production-grade backend requires a centralized, type-safe error handling architecture.

```
                  ┌─────────────────────────────────┐
                  │    HTTP Request in Express      │
                  └────────────────┬────────────────┘
                                   │
                                   ▼
                  ┌─────────────────────────────────┐
                  │ Controller / Service / Repo     │
                  │ Throws an AppError (or subclass)│
                  └────────────────┬────────────────┘
                                   │
                                   ▼
                  ┌─────────────────────────────────┐
                  │     asyncHandler Middleware     │
                  │   Catches rejection & next(err) │
                  └────────────────┬────────────────┘
                                   │
                                   ▼
                  ┌─────────────────────────────────┐
                  │     Global Error Middleware     │
                  │ Formats response to RFC 7807    │
                  └────────────────┬────────────────┘
                                   │
                     ┌─────────────┴─────────────┐
                     ▼                           ▼
        ┌────────────────────────┐  ┌────────────────────────┐
        │  Operational (4xx/5xx) │  │   Programmer (500)     │
        │ Log warning/info       │  │ Log error stack trace  │
        │ Return RFC 7807 JSON   │  │ Alert / Process Restart│
        └────────────────────────┘  └────────────────────────┘
```

## 2. Operational vs Programmer Errors

| Attribute | Operational Errors | Programmer Errors |
| :--- | :--- | :--- |
| **Definition** | Known, expected runtime failure conditions (invalid user input, duplicate record, authentication failure). | Unexpected bugs, missing null checks, syntax errors, failed assertions. |
| **HTTP Range** | 4xx (Client) or intentional 503 (Service Unavailable). | 500 Internal Server Error. |
| **Is Operational** | `isOperational = true` | `isOperational = false` |
| **Action** | Return helpful RFC 7807 envelope to client; do not crash server. | Log full stack trace, capture in APM/Sentry, gracefully restart worker if corrupted. |

## 3. RFC 7807 Problem Details Specification

RFC 7807 defines a standard JSON format for HTTP API error responses:

```json
{
  "type": "https://api.example.com/errors/RESOURCE_NOT_FOUND",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "User with ID 'usr_123' was not found.",
  "instance": "/api/v1/users/usr_123",
  "code": "USER_NOT_FOUND",
  "timestamp": "2026-09-19T09:30:00.000Z"
}
```

### Core Envelope Fields:
- `type`: URI reference identifying the error type.
- `title`: Short, human-readable summary of the error type.
- `status`: HTTP status code.
- `detail`: Human-readable explanation specific to this occurrence of the problem.
- `instance`: URI reference identifying the specific occurrence (request path).
- `code`: Machine-readable domain error code for programmatic client error handling.

## 4. `asyncHandler` Wrapper Pattern

Native Express 4.x routers do not automatically catch rejected Promises returned by `async` request handlers. Without a wrapper or `next(err)` call, an unhandled async error will hang the HTTP request until a client timeout occurs.

```typescript
// Without asyncHandler (Dangerous - hangs request on unhandled rejection)
app.get('/users/:id', async (req, res, next) => {
  const user = await userService.getUser(req.params.id); // If this throws, Express never receives it!
  res.json(user);
});

// With asyncHandler (Safe - automatically forwards error to next(err))
app.get('/users/:id', asyncHandler(async (req, res, next) => {
  const user = await userService.getUser(req.params.id);
  res.json(user);
}));
```

## 5. Global Process Signals (`uncaughtException` & `unhandledRejection`)

- `unhandledRejection`: Fired when a JavaScript Promise rejects and no `.catch()` handler is attached.
- `uncaughtException`: Fired when an unhandled synchronous exception bubbles all the way back to the Node.js event loop.

### Crash Strategy:
When an `uncaughtException` occurs, Node.js process state is non-deterministic (memory/state could be corrupted). The process must:
1. Log the fatal error stack trace.
2. Stop accepting new connections.
3. Allow ongoing requests a short grace period to finish (graceful shutdown).
4. Exit with code `1` so process managers (Docker, Kubernetes, PM2) spawn a fresh clean instance.
